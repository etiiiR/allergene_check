# Privacy and end-to-end encryption plan

Status (2026-10-09): the browser vault and local personal-data path are wired; the server sends only the opaque vault envelope to Inertia. Existing plaintext data has an explicit import path; the first confirmed vault save removes the old primary records transactionally. The seeded legacy-migration integration test and all 53 browser tests have passed against disposable SurrealDB instances. Encrypted backup download/restore and credential rotation are tested. This is still not production-ready: account authorization/remote access, operational recovery drills, real-device testing, and real-user research remain open.

## What the current code does

- Onboarding suggests an editable pseudonym. It is a display name, not an account credential; it and the profile are encrypted inside the diary after setup.
- New or migrated diaries are stored as one revisioned encrypted envelope. The server cannot read recipe names, timestamps, symptoms, notes, stool observations, imported health data, or cycle information from that envelope.
- Inertia sends only the vault envelope and static food/symptom labels. Personal CRUD, ingredient normalization, reporting, and pattern analysis run locally after unlock. The logistic model is exploratory and is not clinically validated.
- Optional manual stress and sleep fields remain empty unless entered. Context values from older records without an explicit confirmation marker are retained but excluded from stress/sleep analysis until the user reviews them. Missing values are not treated as zero stress or standard sleep.
- Plaintext API routes are blocked. A one-time `/api/legacy/diary` read requires an explicit migration header and is available only before vault setup. The confirmed first save checks the revision, stores the ciphertext, and deletes the old primary diary rows in the same SurrealDB transaction. Legacy exports, snapshots, and backups are not automatically purged.
- The vault endpoint has revision compare-and-swap backed by an interactive SurrealDB transaction. It has no account authentication or per-person authorization; it protects write integrity, not access control or availability. This remains a single-person, self-hosted design.
- The recipe crawler still receives a URL when the user explicitly imports a recipe. Recipe text and symptoms remain local during ingredient matching and analysis. Direct cross-origin fetching is generally unavailable, so the URL-disclosure notice remains important.
- Compose now isolates SurrealDB on an internal network shared only with Fiber. The recipe crawler uses a separate internal app link and an egress network for public recipe URLs; it cannot resolve or route to the database network. The CI stack smoke test checks both service-name resolution and direct database-IP reachability.
- The app, database, and ML host ports in Compose are bound to loopback only. Direct Go startup now keeps `LISTEN_HOST=127.0.0.1` in typed configuration and has a regression test; Compose explicitly binds Fiber to all interfaces only inside its container. These local-only defaults do not provide user authentication.
- Local Compose and direct Go startup no longer fall back to the public `root` / `root` database credentials. `sh setup-local-env.sh --new` creates a random 256-bit password in a private, Git-ignored `.env` for a new, empty volume; existing volumes must keep their current credential until it is deliberately rotated. The app fails closed if either credential is absent. This is local credential hygiene, not user authentication or permission for remote deployment.
- The iOS HealthKit bridge now sends imported measurements through the local vault API rather than to the Python analysis service.
- The Python container runs as UID 10001 and sets Hugging Face to offline mode at runtime after caching the pinned BERT model during image build; the CI Compose smoke test checks the unprivileged identity and a CPU-only inference.
- Browser responses now apply a restrictive Content Security Policy (`default-src 'self'`, no objects/frames, same-origin scripts/connections) plus `nosniff`, frame denial, and no-referrer headers. Inline styles remain allowed because Vue currently emits dynamic style attributes. HSTS is not set because TLS termination is deployment-specific. The loopback host guard and same-origin check now use Fiber's parsed request authority; regression tests cover valid local, rejected foreign-host, and same-origin requests. These safeguards are not user authentication or encryption. The app is documented as a single-person local app with no accounts.

## Privacy goals and limits

The target is to keep diary contents unreadable to the database and application server while stored or backed up, with encryption and decryption performed on the trusted user's device. The server may still observe that a pseudonymous vault exists, request timing, ciphertext size, and the user's network address. A pseudonym is not anonymity: distinctive recipes, dates, and other outside information can identify someone.

Browser-based encryption cannot protect against a compromised device, keylogger, malicious browser extension, XSS, or a server that deliberately ships modified JavaScript to steal an unlocked key. It also does not provide account authorization, safe remote access, availability, or protection for old plaintext backups. HTTPS and a clear threat model remain necessary. The UI and documentation must not promise more than this.

## Intended design

1. Generate a random 256-bit data-encryption key on-device. Encrypt the complete diary as one versioned vault using Web Crypto AES-GCM with a fresh random nonce for every encryption. Keep identifiers, profile, recipes, timestamps, symptoms, notes, imported health data, and analysis inputs inside that encrypted payload.
2. Protect the data key with a user passphrase using versioned PBKDF2-HMAC-SHA-256 at 600,000 iterations in the browser's built-in Web Crypto API for the first vault format. OWASP currently recommends this PBKDF2 work factor. Argon2id is a stronger memory-hard candidate for a later format if a maintained browser implementation can be pinned, reviewed, and tested on supported iPhones. Never silently change KDF parameters; benchmark unlock time and bound server-supplied parameters to prevent denial of service.
3. Offer a separate high-entropy recovery key that can also wrap the data key. Show it once, require confirmation that it was saved, and explain clearly that losing both passphrase and recovery key means permanent data loss. The Profile → Sicherheit flow changes both credentials by generating a fresh data key, re-encrypting the local diary, and asking the user to confirm the replacement recovery phrase before writing the new envelope. A failed save keeps the old vault usable; stale edits cannot be overwritten. Previously downloaded backups remain protected by their original credentials and are not silently rewritten.
4. Store one opaque, revisioned ciphertext envelope server-side rather than separate readable rows. Keep only unavoidable transport metadata outside it. Use revision/ETag checks so two tabs cannot silently overwrite one another; resolve stale updates on the client.
5. Decrypt in the browser only after unlock. Keep the non-extractable data key out of Vue state, URLs, logs, Inertia props, localStorage, and analytics. Read passphrase/recovery credentials from password inputs, keep setup keys and legacy plaintext in non-reactive component variables, and clear those on completion/unmount. Lock explicitly and after inactivity; store only encrypted offline queues. The unlocked diary necessarily remains in browser JavaScript memory, and JavaScript cannot guarantee secure memory erasure, so describe that limitation.
6. Run pattern analysis, ingredient normalization, report generation, and any BERT inference on-device. The current Python analysis path must not receive decrypted diary data. The browser recipe importer should fetch directly where the source permits it; any proxy fallback must disclose that the URL/content is sent to that service. The iOS HealthKit bridge must encrypt records before network transfer.
7. Replace plaintext `/api/diary`, `/api/export`, CRUD, health, and analysis paths with an authenticated opaque-vault API. Do not leave a hidden plaintext endpoint available after migration. Plaintext export, if retained, must be explicitly created after local decryption and clearly warned; the default backup should remain encrypted.

## Safe migration and release order

1. Agree and test the key/recovery experience, including passphrase loss, account/device changes, and lock behavior.
2. Build and test the client crypto module against known test vectors, wrong keys, modified ciphertext, nonce handling, and full diary round-trips. Select and pin a maintained KDF package only after dependency and iOS-browser performance review.
3. Add a server endpoint that stores and returns only an opaque encrypted vault, with revision conflicts and access control. Opaque storage and transaction-backed compare-and-swap exist; authorization remains outstanding. Keep it unavailable for public deployment until authentication and HTTPS are in place.
4. Move all frontend personal-data paths to the unlocked client vault. Core CRUD, ingredient normalization, pattern analysis, reports, and HealthKit imports now use this path. Verify with unique sentinels in HTTP logs, application logs, database records, ML requests, Inertia props, and backups.
5. Migrate existing records by explicit user action: load on-device, encrypt, write and verify the vault, and remove primary plaintext rows transactionally. This flow is implemented but needs a live SurrealDB migration test. Do not automatically delete database snapshots, exports, or backups: they may be the only recoverable copy. Purging historical plaintext requires a separate retention decision.
6. Add security review and release gates: authentication/authorization, HTTPS, CSP/XSS hardening, dependency review, safe error/log handling, encrypted backups, recovery drills, concurrency tests, mobile HealthKit tests, and a user-facing privacy explanation. Keep the app marked local-only until these gates pass.

## Current verification

- The five-star symptom component preserves the existing 0–10 analysis/API data while displaying a 0–5 rating.
- New profiles receive an editable pseudonym suggestion; existing names are not silently changed.
- A browser regression now edits a sentinel pseudonym through the profile UI and verifies that neither it nor the vault passphrase appears in any outgoing request body during the save flow.
- Setup and profile now explain in plain language that a pseudonym is not anonymity, the server stores diary content as an encrypted vault, and what encryption does not cover. The longer threat-model notes stay in a native inline disclosure rather than interrupting setup with a modal.
- A version-1 browser vault encrypts the complete diary with AES-GCM, wraps its data key with a passphrase and one-time recovery key, and rejects incorrect keys or modified ciphertext. The non-extractable data key is outside Vue state, localStorage, URLs, and Inertia props. Passphrase/recovery inputs remain in password-field DOM values; staged setup keys and imported legacy plaintext are held in non-reactive component variables and cleared after use or unmount. The unlocked diary remains in browser memory until the session locks manually or after inactivity.
- Envelope validation fixes the KDF parameters at the supported version and bounds salt, nonce, key-wrap, recovery-key, and ciphertext fields before key derivation or base64 decoding. The API also refuses oversized vaults when reading stored data; regression tests cover both client rejection and server read limits.
- Profile → Sicherheit supports credential replacement with a fresh data key and recovery phrase. Confirmation is required before the ciphertext is replaced; regression tests verify the old credentials stop opening the current vault, both new credentials work, failed saves preserve the old vault, and stale prepared changes cannot overwrite newer diary edits.
- The inactivity lock now re-checks wall-clock elapsed time when a hidden tab or back-forward-cache page becomes visible again, compensating for mobile browser timer throttling. A non-modal warning appears one minute before the 15-minute lock; a deliberate continue action or other real interaction resets the timer, while passive restoration does not.
- `GET/PUT /api/vault` stores the opaque envelope with expected-revision checks. Migration requires explicit confirmation and deletes the primary legacy records in the same transaction as the first vault save. Go unit tests cover revision conflicts, malformed requests, and disabled plaintext routes; opt-in SurrealDB integration tests cover competing writers and a seeded legacy migration.
- A GitHub Actions release gate is configured for Go race/static checks, frontend unit/build checks, Python tests with the pinned CPU-only BERT model, a full Compose runtime smoke test (including the blocked plaintext route and local-only BERT inference), SurrealDB integration tests, and mobile/responsive/accessibility browser tests against dedicated ephemeral test databases. Local edits have not yet been observed on a hosted GitHub Actions run.
- The browser now performs CRUD, normalization, reports, and exploratory logistic analysis locally. Forty-eight frontend unit tests, `go test -race ./...`, `go vet ./...`, and the production asset build pass in the current workspace.
- All 53 Playwright tests passed on 2026-10-09 against two disposable SurrealDB 3.3.0 databases and separate source/restore apps. Coverage includes responsive pages, recipe import and 200-recipe search, editing, encrypted-vault persistence across browser contexts, encrypted-backup download and empty-vault restore, credential rotation with both new credentials and rejection of old ones, failed-save/stale-edit safety, manual locking at 320px, and the accessible non-modal pre-lock warning. This does not prove recovery from a real device loss.
- The Go integration suite also passed against an isolated database. Its migration case seeds every primary legacy diary table, verifies a stale-revision rejection preserves the rows, then verifies a successful vault save removes them. The UI restore test confirms an invalid passphrase leaves the destination empty, a valid passphrase restores the profile, and server storage still contains only ciphertext. Backup/recovery drills, manual assistive-technology and device checks, and the planned five-person usability study remain open. A hosted CI result has not been confirmed. Do not advertise this build as production-ready or as protecting historical plaintext backups.
