# Privacy and end-to-end encryption plan

Status (2026-10-15): the browser vault and local personal-data path are wired; the server sends only the opaque vault envelope to Inertia. Existing plaintext data has an explicit import path; the first confirmed vault save removes the old primary records transactionally. A one-account pseudonymous sign-in MVP gates pages and APIs, creates revocable per-device sessions, and keeps its account password separate from the client-side vault passphrase. Profile → Sicherheit can revoke all other sessions while preserving the current one; online tabs check authorization about every 30 seconds and lock after a revocation is observed. The current local Go, frontend, SurrealDB integration, and 55-test browser suites pass against disposable databases. This is still not production-ready: account-password recovery, a per-device session inventory, operational recovery drills, real-device testing, independent security review, and real-user research remain open.

## What the current code does

- Onboarding suggests an editable pseudonym. It is a display name, not an account credential; it and the profile are encrypted inside the diary after setup.
- New or migrated diaries are stored as one revisioned encrypted envelope. The server cannot read recipe names, timestamps, symptoms, notes, stool observations, imported health data, or cycle information from that envelope.
- Inertia sends only the vault envelope and static food/symptom labels. Personal CRUD, ingredient normalization, reporting, and pattern analysis run locally after unlock. The logistic model is exploratory and is not clinically validated.
- Optional manual stress and sleep fields remain empty unless entered. Context values from older records without an explicit confirmation marker are retained but excluded from stress/sleep analysis until the user reviews them. Missing values are not treated as zero stress or standard sleep.
- Plaintext API routes are blocked. A one-time `/api/legacy/diary` read requires an explicit migration header and is available only before vault setup. The confirmed first save checks the revision, stores the ciphertext, and deletes the old primary diary rows in the same SurrealDB transaction. Legacy exports, snapshots, and backups are not automatically purged.
- The vault endpoint has revision compare-and-swap backed by an interactive SurrealDB transaction. A single pseudonymous account now gates diary pages, APIs, and WebSockets. Account passwords are stored as salted PBKDF2-HMAC-SHA-256 hashes; random 30-day session cookies are HttpOnly, SameSite Strict, Secure when `APP_URL` is HTTPS, and stored server-side only as SHA-256 digests so a database read does not disclose reusable session tokens. A one-time bootstrap code permits only first-account setup. Login attempts are rate-limited per process with bounded memory (4,096 source-address buckets and periodic expiry cleanup); saturation rejects new addresses instead of dropping another address's active limit. This is not shared across server replicas and remains unsuitable as the only control for a horizontally scaled public deployment. This is one account for one personal diary, not multi-user tenancy; multi-device access means multiple devices sign in to the same encrypted vault.
- The recipe crawler still receives a URL when the user explicitly imports a recipe. Recipe text and symptoms remain local during ingredient matching and analysis. Each crawler and `robots.txt` request now resolves and validates all DNS answers, pins the actual connection to a public IP while preserving the original HTTP Host/TLS certificate hostname, disables environment proxies, revalidates redirects, and bounds both HTML and robots responses. This closes DNS-rebinding and proxy-bypass paths to private services; direct cross-origin fetching is generally unavailable, so the URL-disclosure notice remains important.
- Compose now isolates SurrealDB on an internal network shared only with Fiber. The recipe crawler uses a separate internal app link and an egress network for public recipe URLs; it cannot resolve or route to the database network. The CI stack smoke test checks both service-name resolution and direct database-IP reachability.
- The app, database, and ML host ports in Compose are bound to loopback only. Direct Go startup defaults to `LISTEN_HOST=127.0.0.1`; Compose binds Fiber to all interfaces only inside its container. Remote access is intended through an HTTPS reverse proxy with exact `APP_URL` and preserved `Host`; startup rejects a non-local HTTP origin. Never publish the app container port directly as a substitute for HTTPS.
- Local Compose and direct Go startup no longer fall back to the public `root` / `root` database credentials. `sh setup-local-env.sh --new` creates a random database password and a separate 256-bit one-time account setup token in a private, Git-ignored `.env`; `sh setup-auth-token.sh` adds the setup token to an existing `.env` without replacing database credentials. Existing volumes must keep their current database password until deliberately rotated. The server fails closed if the one-time setup token is missing or too short.
- The iOS HealthKit bridge now sends imported measurements through the local vault API rather than to the Python analysis service.
- The Python container runs as UID 10001 and sets Hugging Face to offline mode at runtime after caching the pinned BERT model during image build; the CI Compose smoke test checks the unprivileged identity and a CPU-only inference.
- Browser responses now apply a restrictive Content Security Policy (`default-src 'self'`, no objects/frames, same-origin scripts/connections, and `style-src-attr 'none'`) plus `nosniff`, frame denial, and no-referrer headers. Three dynamic Vue style bindings were replaced with CSS-driven progress elements, so inline style attributes are no longer allowed. HSTS is not set because TLS termination is deployment-specific. The loopback host guard and same-origin check use Fiber's parsed request authority and require the configured public scheme/host, including when HTTPS terminates at a reverse proxy. These safeguards complement, but do not replace, account authorization, HTTPS, or E2EE.

## Privacy goals and limits

The target is to keep diary contents unreadable to the database and application server while stored or backed up, with encryption and decryption performed on the trusted user's device. The server may still observe that a pseudonymous vault exists, request timing, ciphertext size, and the user's network address. A pseudonym is not anonymity: distinctive recipes, dates, and other outside information can identify someone.

Browser-based encryption cannot protect against a compromised device, keylogger, malicious browser extension, XSS, or a server that deliberately ships modified JavaScript to steal an unlocked key. Account authentication controls who can fetch ciphertext but does not recover the vault passphrase. The MVP has no account-password reset flow or per-device session inventory; bulk revocation of all other sessions is available, and the bounded login limiter is in-memory per process. A multi-replica deployment needs a shared rate limiter and coordinated session operations. Losing the account password currently requires an operator-assisted account reset, while losing both vault credentials still means permanent data loss. HTTPS and a clear threat model remain necessary. The UI and documentation must not promise more than this.

## Intended design

1. Generate a random 256-bit data-encryption key on-device. Encrypt the complete diary as one versioned vault using Web Crypto AES-GCM with a fresh random nonce for every encryption. Keep identifiers, profile, recipes, timestamps, symptoms, notes, imported health data, and analysis inputs inside that encrypted payload.
2. Protect the data key with a user passphrase using versioned PBKDF2-HMAC-SHA-256 at 600,000 iterations in the browser's built-in Web Crypto API for the first vault format. OWASP currently recommends this PBKDF2 work factor. Argon2id is a stronger memory-hard candidate for a later format if a maintained browser implementation can be pinned, reviewed, and tested on supported iPhones. Never silently change KDF parameters; benchmark unlock time and bound server-supplied parameters to prevent denial of service.
3. Offer a separate high-entropy recovery key that can also wrap the data key. Show it once, require confirmation that it was saved, and explain clearly that losing both passphrase and recovery key means permanent data loss. The Profile → Sicherheit flow changes both credentials by generating a fresh data key, re-encrypting the local diary, and asking the user to confirm the replacement recovery phrase before writing the new envelope. A failed save keeps the old vault usable; stale edits cannot be overwritten. Previously downloaded backups remain protected by their original credentials and are not silently rewritten.
4. Store one opaque, revisioned ciphertext envelope server-side rather than separate readable rows. Keep only unavoidable transport metadata outside it. Use revision/ETag checks so two tabs cannot silently overwrite one another; resolve stale updates on the client.
5. Decrypt in the browser only after unlock. Keep the non-extractable data key out of Vue state, URLs, logs, Inertia props, localStorage, and analytics. Read passphrase/recovery credentials from password inputs, keep setup keys and legacy plaintext in non-reactive component variables, and clear those on completion/unmount. Lock explicitly and after inactivity; store only encrypted offline queues. The unlocked diary necessarily remains in browser JavaScript memory, and JavaScript cannot guarantee secure memory erasure, so describe that limitation.
6. Run pattern analysis, ingredient normalization, report generation, and any BERT inference on-device. The current Python analysis path must not receive decrypted diary data. The browser recipe importer should fetch directly where the source permits it; any proxy fallback must disclose that the URL/content is sent to that service. The iOS HealthKit bridge must encrypt records before network transfer.
7. Replace plaintext `/api/diary`, `/api/export`, CRUD, health, and analysis paths with an authenticated opaque-vault API. Do not leave a hidden plaintext endpoint available after migration. Plaintext export, if retained, must be explicitly created after local decryption and clearly warned; the default backup should remain encrypted.

## Safe migration and release order

1. Agree and test the key/recovery experience, including passphrase loss, account/device changes, and lock behavior.
2. Build and test the client crypto module against known test vectors, wrong keys, modified ciphertext, nonce handling, and full diary round-trips. Select and pin a maintained KDF package only after dependency and iOS-browser performance review.
3. Add a server endpoint that stores and returns only an opaque encrypted vault, with revision conflicts and access control. Opaque storage, transaction-backed compare-and-swap, single-account authentication, and bulk revoke-other-sessions exist. Complete account-password recovery, a per-device session inventory, reverse-proxy deployment review, and independent security review before public deployment.
4. Move all frontend personal-data paths to the unlocked client vault. Core CRUD, ingredient normalization, pattern analysis, reports, and HealthKit imports now use this path. Verify with unique sentinels in HTTP logs, application logs, database records, ML requests, Inertia props, and backups.
5. Migrate existing records by explicit user action: load on-device, encrypt, write and verify the vault, and remove primary plaintext rows transactionally. The live SurrealDB integration test verifies that stale writes preserve legacy rows and a successful migration removes them in the same transaction. Do not automatically delete database snapshots, exports, or backups: they may be the only recoverable copy. Purging historical plaintext requires a separate retention decision.
6. Add security review and release gates: independent authentication/authorization review, verified HTTPS deployment, CSP/XSS hardening, dependency review, safe error/log handling, account recovery, device-session revocation, encrypted backups, recovery drills, concurrency tests, mobile HealthKit tests, and a user-facing privacy explanation. Keep the app marked as an MVP until these gates pass.

## Current verification

- The five-star symptom component preserves the existing 0–10 analysis/API data while displaying a 0–5 rating.
- New profiles receive an editable pseudonym suggestion; existing names are not silently changed.
- A browser regression now edits a sentinel pseudonym through the profile UI and verifies that neither it nor the vault passphrase appears in any outgoing request body during the save flow.
- Setup and profile explain in plain language that a pseudonym is not anonymity, the server stores diary content as an encrypted vault, and what encryption does not cover. The privacy summary now also clearly separates account sign-in (access to ciphertext) from the vault passphrase/recovery phrase (decryption); the updated profile copy has a focused browser regression. The longer threat-model notes stay in a native inline disclosure rather than interrupting setup with a modal. Profile → Sicherheit offers bulk revocation of all other sessions; active tabs check the protected session endpoint on focus, visibility, and a 30-second interval, then lock the local vault on a 401. Network failures do not masquerade as revocation. This is not a per-device inventory or selective revoke.
- A version-1 browser vault encrypts the complete diary with AES-GCM, wraps its data key with a passphrase and one-time recovery key, and rejects incorrect keys or modified ciphertext. The non-extractable data key is outside Vue state, localStorage, URLs, and Inertia props. Passphrase/recovery inputs remain in password-field DOM values; staged setup keys and imported legacy plaintext are held in non-reactive component variables and cleared after use or unmount. The unlocked diary remains in browser memory until the session locks manually or after inactivity.
- Envelope validation fixes the KDF parameters at the supported version and bounds salt, nonce, key-wrap, recovery-key, and ciphertext fields before key derivation or base64 decoding. The API also refuses oversized vaults when reading stored data; regression tests cover both client rejection and server read limits.
- Profile → Sicherheit supports credential replacement with a fresh data key and recovery phrase. Confirmation is required before the ciphertext is replaced; regression tests verify the old credentials stop opening the current vault, both new credentials work, failed saves preserve the old vault, and stale prepared changes cannot overwrite newer diary edits.
- The inactivity lock now re-checks wall-clock elapsed time when a hidden tab or back-forward-cache page becomes visible again, compensating for mobile browser timer throttling. A non-modal warning appears one minute before the 15-minute lock; a deliberate continue action or other real interaction resets the timer, while passive restoration does not.
- `GET/PUT /api/vault` stores the opaque envelope with expected-revision checks and now requires a valid account session in the running server. First-account setup uses a one-time high-entropy environment token; the account password and vault phrase are separate. Login sets a server-stored, revocable session cookie; users can revoke the current session by logging out or revoke all other sessions while preserving the current one. Migration requires explicit confirmation and deletes primary legacy records in the same transaction as the first vault save. Go tests cover account hashing/session/cookie behavior, revision conflicts, malformed requests, and disabled plaintext routes; opt-in SurrealDB integration tests cover competing writers and a seeded legacy migration.
- A GitHub Actions release gate is configured for Go race/static checks, frontend unit/build checks, Python tests with the pinned CPU-only BERT model, a full Compose runtime smoke test (including the blocked plaintext route and local-only BERT inference), SurrealDB integration tests, and mobile/responsive/accessibility browser tests against dedicated ephemeral test databases. Local edits have not yet been observed on a hosted GitHub Actions run.
- The browser now performs CRUD, normalization, reports, and exploratory logistic analysis locally. Fifty-six frontend unit tests, `go test ./...`, and the production asset build pass in the current workspace. Earlier Go race and vet checks are recorded in CI/history and should be rerun for release.
- Symptom check-ins now carry an explicit `food_relation`. Existing records without the field retain window-matching behavior; new records can opt out so nearby meals are excluded from ingredient analysis while the symptom moment remains available to non-food and context summaries. The editor and diary label this choice. Browser coverage is added but not run locally; the focused Python test could not be collected because NumPy is absent from the available temporary environment.
- All 55 Playwright tests passed on 2026-10-15 against two freshly initialized, memory-only SurrealDB 3.3.0 databases and separate source/restore apps. Coverage includes second-device sign-in and revocation, responsive pages, CSP violations, recipe import and 200-recipe search, editing, encrypted-vault persistence across browser contexts, encrypted-backup download and empty-vault restore, credential rotation, failed-save/stale-edit safety, manual locking, and the accessible non-modal pre-lock warning. A new sparse-sample Insights regression has been added but not run because this workspace has no isolated app on port 3001 and Docker access was unavailable. Previous passing browser results do not verify this new UI change or prove recovery from a real device loss.
- The opt-in Go integration suite passed on 2026-10-15 against an isolated `_tests` database, including transaction rollback/live query, concurrent vault revision checks, explicit legacy migration, and hashed account-session persistence. The migration case verifies a stale-revision rejection preserves legacy rows and a successful vault save removes primary plaintext rows transactionally. The UI restore test confirms an invalid passphrase leaves the destination empty, a valid passphrase restores the profile, and server storage still contains only ciphertext. Backup/recovery drills, manual assistive-technology and device checks, independent security review, and the planned five-person usability study remain open. A hosted CI result has not been confirmed. Do not advertise this build as production-ready or as protecting historical plaintext backups.
